# 인수인계

다음 세션에서 이 프로젝트를 이어받을 때 **작업을 시작하기 전에 읽는 문서**다.
여기는 길잡이만 있다 — 내용은 전부 다른 문서에 있고, 같은 것을 두 곳에 적지
않는다 (그게 이 저장소의 1번 실패 원인이다).

> 프로젝트가 **무엇을 하는 것인지**부터 잡으려면 `concepts.md` 를 먼저 본다.

## 0. 작업 대상은 오피스 섹터 하나다

**활성 씬은 4번 `office-sector`** (회사 사옥 지하 1층, 첫 실내 씬) 이고,
**앞으로의 작업은 이 씬에만 한다** (2026-08-03 사용자 결정).
이 씬은 **게임의 오프닝 무대**다 — 스토리와 모델링 목표는
[`scenes/office-sector/story.md`](scenes/office-sector/story.md) (2026-08-05 확정).

나머지 세 씬 — 공터·나이트시티·모델테스트 — 은 **동결**이다. 돌아갈 계획이
없고 백로그도 없다. 값어치는 거기서 학습한 데이터다: `lessons.md` 의 규칙,
씬별 지식 문서, core 로 굳은 코드. **참조는 하되 고치지 않는다.**

| | |
|---|---|
| 오피스 — 형태의 근거 | [`scenes/office-sector/facility.md`](scenes/office-sector/facility.md) — **치수를 고치기 전에 읽는다** |
| 오피스 — 생성기 구조·남은 일 | [`scenes/office-sector/status.md`](scenes/office-sector/status.md) |
| 동결 씬의 지식 | 각 씬의 `status.md` 가 "지식이 어디 있나" 표를 들고 있다 |

## 1. 5분 안에 파악하기

```bash
cd web && npm install          # 처음 한 번 (node_modules 는 커밋 안 한다)
node web/server.mjs
# http://localhost:5173        활성 씬 = 오피스 섹터
```

브라우저 콘솔:

```js
__audit()          // 예산·규약·개수·배치 점검 — 경고 0건이 정상
__place()          // 배치 결함이 어디서 났는지
await __lock()     // 현재 씬의 검증 뷰를 shots/ 에 렌더
```

```bash
node tools/verify.mjs office-sector   # 기준선과 픽셀 비교
```

**작업 시작 전에 "전부 일치" 인지 확인한다.** 아니면 누가 뭘 바꾸고 기준선을
안 잡은 것이고, 그 상태로 작업하면 원인 추적이 불가능해진다.

**형태를 만들기 전에 근거 문서부터, 코드를 고치기 전에 규칙부터.** 이
프로젝트에서 가장 크게 실패한 지점이 "형태를 만들고 설명을 갖다 붙인 것"
(nightcity `city.md` 의 '정정' 절)과 "이미 있는 것 위에 덮어쓰기" 다.

## 3. 일하는 규약

- **형태 → 실배치·검증 → 디테일** 순서로 간다. 3단계는 물건마다 "그 물건로
  만드는 조각 서너 개" 를 적고 그것에 대고 확인한 뒤에 완료라고 쓴다
  (`lessons.md` 3.13.1 — 이름만 붙이고 완료로 썼다가 두 번 만든 적이 있다).
- **커밋은 사용자가 시킬 때만.** 검증하고 보고한 뒤 멈춘다.
- 값의 출처는 하나다. 치수는 `facility.md` → `layout.js`, 두 모듈이 같은
  숫자를 알아야 하면 위로 올린다. 주석으로 "같아야 한다" 라고 쓰지 않는다.
- 놓기 전에 그 자리에 무엇이 있는지 묻는다. 지오메트리를 만드는 모듈은
  `b.mark()` 를 걸어 배치 원장에 올린다.
- 새 카운트를 만들면 `audit.js` 의 `EXPECT` 하한과 씬의 `counts` 신고를
  같이 단다. 모듈 수준 캐시를 만들면 `onSceneReset()` 에 등록한다.
