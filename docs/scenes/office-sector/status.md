상호작용 소품은 개별 노드다 (게임의 개별 콜라이더·크랙·약탈 포즈 요구 —
`props.js` interactSet 머리말). 분리 도입 때 실측 3.9ms/frame 으로 감당
범위임을 확인했다.

**약탈 열림 포즈 186벌** (카튼·상자·배전반·랙·책상 서랍·사물함 — 닫힘과
같은 번호, `rack_07_open`). 씬에는 안 붙어 화면 비용이 0 이고, 굽기·
익스포트만 탄다 — 열림 상태를 열림 포즈 그대로 구우므로 상자 속까지 맞는
빛이 든다. 유니티가 약탈 시 닫힘/열림을 1프레임에 토글한다 (`spawnPair`
머리말).

> **이름의 안정성 주의** — `rack_07` 의 번호는 생성 **순서**에서 나온다. 같은
> 코드는 같은 번호를 내지만, 평면·밀도를 바꾸면 번호가 통째로 밀린다. 게임
> 세이브가 이 이름으로 소품 상태를 저장하기 시작하면 배치 변경이 세이브를
> 깨뜨린다 — **세이브 참조는 배치가 확정된 뒤에만**, 아니면 좌표 해시 기반
> 안정 ID 를 따로 낸다.

**브라우저에서 확인**: 프리캠으로 물건에 2.4m 안까지 다가가면 하단에
`[E] 서버 랙 rack_07 열기` 힌트가 뜨고 E 가 포즈를 토글한다
(`src/interact.js` — 대상이 잡힌 동안만 E 를 가로채고, 평소엔 상승 그대로).
익스포트·`__lock` 은 시작 전에 전부 닫힘으로 되돌리므로 열어 둔 채 내보내도
결과가 어긋나지 않는다.

## 2. 생성기의 구조 — 어디를 고치면 무엇이 바뀌나

```
layout.js    평면의 유일한 출처. 칸 · 치수 · 벽 규칙 · 평면 검사
duct.js      탈출 덕트의 유일한 출처 — 계획(ductPlan)과 검사(checkDuct)
  ├ shell.js     바닥 · 벽(덕트 포트 개구 포함) · 천장 · 암반(공동구 포함)
  ├ props.js     소품 (용도별) — 배경은 병합, 상호작용 소품은 물건마다 노드
  ├ lights.js    등과 광원의 자리 (좌표만)
  │   └ bake.js      그 자리에서 빛을 정점에 굽는다
  ├ materials.js 재질 묶음  ← textures.js 가 굽는 레시피를 쓴다
  └ check.js     실내 전용 검사 (캄캄한 방 · 머리 닿음 · 조도 위계)
index.js     위를 순서대로 부르고, 결함을 배치 검사에 넘긴다
```

### 2.1 layout.js — 여기가 평면이다

| 내보내는 것 | 무엇 |
|---|---|
| `H` `W` `FLOOR` | 치수. facility.md 2장의 표가 그대로 온다 |
| `CELLS` | 축에 나란한 사각형 15개. `kind`(벽·조명 규칙) 와 `use`(소품) 가 따로다 |
| `PAIR` | 두 `kind` 사이에 무엇이 서나 — open/door/wide/glass/solid |
| `wallRuns()` | 층 전체의 **벽** 구간. 한 경계를 두 번 안 짓는다 |
| `openness()` | 칸 사이가 얼마나 트였나 (**가공 전** 규칙). 도달 검사와 빛 굽기가 같이 쓴다 |
| `interiorWalls(id)` `onWall(w,t,d)` | 소품이 붙을 면. 문 자리는 이미 빠져 있다 |
| `checkPlan()` `checkReach()` | 겹침 · 층 채움 · 갇힌 방 |

**새 섹터를 만들려면** `CELLS` 와 `PAIR`, 그리고 `props.BY_USE` 의 용도 몇 개만
고치면 된다는 것이 이 판의 가설이다 (6장, 아직 미검증).

### 2.2 벽에 구멍은 불리언으로 안 뚫는다

칸의 경계를 훑어 **이웃이 같은 구간으로 쪼개고**, 규칙표를 보고 열지 말지
정한다. 도시의 `streetFaces` 와 같은 자리다.

```
edgeSpans()  경계를 이웃이 바뀌는 지점마다 자른다 -> 같은 이웃끼리 합친다
wallRuns()   층 전체의 벽 구간
openingsOf() 그 구간에 뚫릴 문
```

합치기를 안 했더니 68구간이 나왔다 — 마주보지도 않는 칸의 경계값이 벽을
셋으로 쪼개 **18m 벽 하나에 문이 세 개** 섰다. 합친 뒤 40구간.

**소핏** — 플라자(5.6)를 고리 복도(2.7)가 감싼다. 바닥에서는 트여 있지만 그
사이에 2.9m 수직면이 생긴다. 안 세우면 복도 천장 위 설비가 들여다보인다.

### 2.3 조명 — 좌표는 하나, 쓰는 곳은 셋

```
lights.lightPlan()   등과 광원의 자리를 낸다 (지오메트리도 THREE 객체도 안 만듦)
  ├ createFixtures()   보이는 것 — 발광판 + 반사갓
  ├ bake.bakeVertexLight()   밝히는 것 — 정점 컬러로 굽는다   ← 기본
  └ createRealLights()       밝히는 것 — 실시간 PointLight    ← bake.BAKED = false
```

두 조명 경로가 **같은 계획과 같은 지오메트리**를 쓰므로, A/B 화면 차이는
오로지 조명 차이다. 굽기 근사 셋:

| | |
|---|---|
| 등은 **아래를 보는 면** | 반지름 0.7m 구로 본다. 점으로 두면 가까이서 발산해 정점 하나만 튄다. 배광에 바닥(0.32)을 깔아 등과 같은 높이의 덕트도 받게 했다 |
| 칸 사이는 **틈의 높이**로 막는다 | 플라자의 등이 고리 복도 바닥을 못 비추는 것이 이 한 줄이다 — 소핏이 막는다. 가로 위치는 트인 비율로 뭉갠다 |
| 바운스는 **바닥에서 온다** | 아래를 보는 면이 제일 많이 받고 높이가 오를수록 준다 |

**정점 간격이 곧 라이트맵 해상도다.** `MeshBuilder({span})` 으로 상자를 쪼갠다
— 벽 1.2m · 바닥 1.5m · 천장 3.0m. 천장이 제일 성긴 이유는 등이 아래를 보므로
천장이 직사광을 0 으로 받기 때문이다.

레벨은 눈이 아니라 분포로 맞춘다 — 상위 0.5%(p99.5)가 1.0 바로 아래(0.81)에
오도록 `GAIN` 을 잡는다. 그 위는 잘리고, 그 아래로 남기면 계조를 버린다.

### 2.4 무엇을 재나

```
checkPlan()      칸이 겹치나 · 층을 채우나 · 너무 작은 칸이 있나 -> 빌드를 던진다
checkReach()     문 그래프를 BFS. 갇힌 방을 잡는다
checkInterior()  캄캄한 방 · 머리 닿는 통로 · 천장 격자 어긋남
checkLighting()  플라자가 제일 밝나 · 닫힌 복도가 방보다 어둡나 · 폭이 3배는 되나
```

`layout.PAIR` 는 **스스로를 검사한다** — 키가 알파벳순인가, 쓰이는 종류 조합이
다 있는가. 로드하다 두 번 터졌고 둘 다 화면을 보기 전에 잡혔다.

**조도에 반사율을 곱해 잰다.** 구운 값은 "닿은 빛" 이고 보이는 것은 거기에
재질이 한 번 더 곱해진 값이다 — 플라자가 빛을 2배 받고도 화면에서 복도에
밀렸던 것이 이 차이였다 (`lessons.md` 3.10).

## 3. 이 씬이 세운 것

### 계측을 형태보다 먼저

캐릭터 씬에서 **"30뷰 일치, 경고 0" 을 네 번 보고하는 동안 얼굴이 파여
있었다** (`lessons.md` 3.8). 실내는 다행히 전부 숫자로 잡히므로, 이번엔
형태를 짓기 전에 검사부터 만들었다. 그 판단은 값을 했다 — `PAIR` 자기검사 ·
도달 검사 · 소품 수 셋이 각각 화면에 나오기 전에 결함을 잡았다.

**다만 계측이 못 보는 축은 그대로 남았다.** 화면·재질·"그 물건으로 읽히나"
는 숫자가 아니라 사람이 봐야 한다. 이 씬에서 실제로 그렇게 새어 나간 것이
아래 4장 절반이다.

### 인상을 바꾼 것 셋

| | |
|---|---|
| **굽도리** | 바닥에서 1.1m 색이 다른 띠. 위아래가 같으면 복도가 관처럼 보인다. 한 줄로 제일 크게 바뀌었다 |
| **원기둥** | 배관을 상자로 냈더니 천장에 각목이 걸린 것 같았다. **실루엣이 그 물건을 정한다** — 의자 다리·전선관·냉매 배관까지 같은 이야기다 |
| **문 너머가 보인다** | 플라자에서 카페테리아의 식탁과 창고의 선반이 보인다. 실내의 깊이는 여기서 나온다 |

### 4.2 재질이 형태를 먹은 것 — 세 번 반복

세 번 다 같은 병이다. 형태를 고쳐 놓고 화면이 안 변해서 조명을 의심했는데,
구운 값을 재 보면 멀쩡했고 범인은 알베도였다.

| 물건 | 구운 값 | 범인 |
|---|---|---|
| 덕트 | 0.26 (정상) | `metalness 0.45` — 금속은 확산 알베도가 없다 |
| 책상 서랍장 | 정상 | `steelDark` 알베도 0.13 |
| 서버 유닛 U 칸 | 0.25 (정상) | `bezel` 색 `0x40454d` → 알베도 0.056 |

**형태를 나눴는데 안 보이면 조명이 아니라 알베도부터 본다** (`lessons.md` 3.12).

덕트에서는 그 전에 조명을 두 번 고쳤다 — 광원 높이(천장 밑 0.35m 안이 통째로
그늘이었다)와 배광(순수 코사인은 자기 높이를 못 비춘다). **둘 다 맞는
수정이지만 화면은 거의 안 변했고, 그동안 값을 한 번도 안 쟀다.**

### 4.3 좌표 규약을 둘로 둔 것

창고 상자 백여 개가 **옆방 카페테리아 한가운데 공중에** 떠 있었다.

```js
const [px, pz] = wallAt(w, uu, 0.32, 0);   // wallAt 은 [x, y, z] 를 돌려준다
```

`pz` 에 y(=0) 가 들어갔다. 같은 파일의 `onWall` 은 `[x, z]` 를 돌려주므로
규약이 둘이었고 새 것을 옛 습관으로 받았다. 감사도 배치 검사도 통과했다 —
지오메트리는 멀쩡히 있고 겹치지도 않았다.

### 4.4 "디테일" 을 이름만 붙이고 넘어간 것

`status.md` 에 "소품 마감 **완료**" 라고 적었을 때, 컴퓨터는 화면이 몸통
뒷면에 붙어 있었고(34대 전부 사람 반대쪽) 자판기는 색칠한 상자였다.

**핵심 설계 — 광원 없는 씬.** 조명이 정점에 구워져 있으므로 유니티 쪽은
`Custom/BakedVertexColor`(텍스처 x 정점색, 언릿) 하나로 브라우저의
`알베도 x 정점색 x π x (1/π)` 와 같은 식이 된다. 발광·유리는 재질 이름
(결정론적 — core/material.js)으로 골라 glTFast 재질을 그대로 둔다.

블렌더 FBX 경로도 별도 실측했다 — 정점 컬러가 왕복에서 살아남는다
(walls 휘도 0.046~0.789 · props 0.055~0.991, 분산 보존).

## 7. 가설 검증 — 통과 (2026-08-05)

이 판의 가설은 **"되면 나머지 섹터는 같은 생성기에 파라미터만 바꿔 나온다"**
였다. 평면 확장(5.2)이 첫 검증이었고 **통과했다**:

- 고친 것: `layout.CELLS` 사각형 (15칸 → 23칸) + `props.BY_USE` 에 화장실
  생성기 하나. **PAIR·껍데기·조명·굽기·검사·파이프라인은 한 줄도 안 고쳤다.**
- 따라온 것: 벽 40 → 62구간, 문 26, 조명 52, 소품 재배치, 도달·조도 검사,
  약탈 포즈(246)와 익스포트까지 전부 유도.
- 검사가 일한 것: 처음에 방만 쪼갰더니 고리 복도에 안 닿는 외곽 방 넷이
  갇혔다 — `checkReach` 가 화면 보기 전에 잡았고, 답(띠 복도)은 CELLS 안에서
  나왔다. 책상 밀도의 부동소수점 경계(등호 금지 규칙)도 개수 신고가 잡았다.

새 섹터를 만들 때 손댈 곳: `CELLS` · (새 kind 가 생기면) `PAIR` · `BY_USE`
용도 함수. 이 씬에서 실측으로 확인된 사실이다.
