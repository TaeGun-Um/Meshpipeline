# 캐릭터를 코드로 만든다는 것 — 파악된 것

`status.md` 는 시간순 작업 기록이다. 이 문서는 그 다섯 판에서 **남은 것**만
정리한다 — 도구·치수·규칙·결함·비용. 캐릭터를 다시 건드리기 전에 이걸 읽는다.

```
실측 (2026-08-02)
삼각형 61,380 · 텍스처 6장 9.4MB · 재질 13 · 빌드 146ms · 감사 경고 0
캐릭터 부품 145 (그중 아웃라인 껍질 64) · 스킨드 6 · 본 30 · 스프링 2줄
```

---

## 0. 결론부터

| | |
|---|---|
| **코드가 이긴다** | 땋은 머리 · 장식 · 옷의 규칙 있는 부분 · 리그 배관 · 스프링 물리 |
| **코드가 진다** | 얼굴 조형 · 몸의 실루엣 · 텍스처의 결 · 표정 |

이유는 지식이 아니라 **되먹임 고리**다. 숫자를 적고 → 새로고침하고 → 그제야
본다. 모델러는 정점을 잡고 당기면서 본다. 그 차이가 판마다 결함을 남겼고,
다섯 판을 돌아도 수렴하지 않았다.

> **그리고 이 저장소의 검사는 형태를 못 본다.**
> 삼각형·배치 결함·픽셀 회귀 30뷰까지 다 있는데 "이 턱선이 예쁜가" 에는 숫자가
> 없다. 그래서 얼굴 한가운데가 광대보다 11mm 파인 상태로 **"30뷰 일치, 경고 0"
> 을 네 번 보고했다.** 계측이 강한 저장소일수록 계측 밖의 것을 놓친다.

실무 경로는 **하이브리드**다 (6장). 배관은 전부 검증했다.

---

## 1. 도구 — 무엇으로 만드나

캐릭터를 만들며 다섯 모듈이 생겼다. 도시의 상자·원기둥으로는 사람이 안 된다.

| 파일 | 무엇 | 언제 쓰나 |
|---|---|---|
| `surface.js` | **로프트**(높이별 초타원 단면) · **스윕**(경로+단면) · `sampleKeys` · `mirrorX` | 몸통·팔다리·머리·치마는 로프트, 머리카락 가닥·쇄골·뿔은 스윕 |
| `paint.js` | 캔버스 2D 경로로 **그리는** 텍스처 · `taperStroke` · `curve` | 얼굴처럼 좌표의 함수가 아닌 것 |
| `toon.js` | 툰 마스터(단계 램프) · 림 라이트 주입 · **역법선 껍질 아웃라인** | 서브컬처 룩 전부 |
| `spring.js` | 본 사슬 · UV 스키닝 · VRM 식 스프링 | 흔들려야 하는 머리카락 |
| `rigtest.js` | 외부 리깅 GLB 를 불러 코드 생성물을 얹는 진단 | 하이브리드 시험 (`__rig()`) |

### 도구를 고르는 기준

> **로프트는 y 로 쌓는 물건이다. 가로로 누운 것은 못 만든다.**
>
> 쇄골을 로프트로 만들려다 틀렸다 — 링을 y 로 정렬하는 순간 순서가 뒤섞였다.
> 경로를 따라가는 것은 스윕이다. **도구를 고르는 것이 형태를 잡는 것보다 먼저다.**

## 2. 치수 — 단일 출처

같은 값을 두 곳에서 계산하면 어긋난다. 이 씬에서 그 규칙을 **네 번** 어겼다
(5장). 지금은 아래가 유일한 출처다.

| 상수 | 파일 | 무엇을 정하나 | 누가 받나 |
|---|---|---|---|
| `HEAD.bot / top / half` | `head.js` | 머리 구간과 얼굴 텍스처가 덮는 범위 | 얼굴 UV · 머리카락 전부 |
| `HEAD_KEYS` | `head.js` | 두상 실루엣 | 머리 지오메트리 · `headFrontZ` |
| `headFrontZ(y, x, back)` | `head.js` | **그 높이에서 두피가 어디 있나** | 앞머리 · 뒷머리 |
| `F` (brow/eye/cheek/noseTip/…) | `head.js` | 얼굴 뼈 높이 | 얼굴 구조 · 귀 위치 |
| `EYE_V` | `face.js` | 눈 높이 하나 | 코 · 입 · 홍조가 전부 여기서 유도 |
| `Y` (hip/waist/bust/shoulder/…) | `body.js` | 몸의 기준 높이 | 몸통·의상·팔다리 전부 |
| `LEG_KEYS` | `body.js` | 다리 실루엣 | 다리 · **스타킹**(두께만 더함) |
| `BRAID_KEYS` · `BRAID_R0/R1` | `hair.js` | 땋은 머리 중심 경로와 굵기 | 가닥 · 본 자리 · 고리 |

### 비율

```
키 1.60 · 머리 0.248 → 6.5등신     애니가 쓰는 비율
7.4등신으로 뒀더니 마른 성인이었다. 머리가 작으면 그 순간 실사 체형이다.

두상 세로 0.248 x 가로 0.192 = 1.29
실사가 약 1.45. 애니는 그보다 더 둥글다 — 이마가 넓고 턱이 짧다.

눈 높이  턱에서 42%      눈 반폭  머리 폭의 약 1/3
코       눈~턱의 40%     입       눈~턱의 57%
```

## 3. 형태의 규칙

### 3.1 형태를 비율로 곱하지 말 것

이 씬에서 제일 비싼 교훈이다. "정면 평면성" 을 이렇게 구현했었다.

```js
z *= 1 - 0.34 * (1 - |x| / 0.074) ** 2      // 틀렸다
```

곱셈은 **큰 값을 많이 줄인다.** 중앙이 제일 크므로 중앙이 제일 많이 사라진다.
눈높이에서 재 보면 코 자리 0.0815, 광대 0.0926 — 얼굴 한가운데가 광대보다
11mm 뒤였다. 계곡을 파 놓고 그 위에 코를 17mm 얹은 셈이라, 앞선 네 판에서
코를 키우고 뼈를 얹은 것이 전부 효과가 없었다.

**목표 형태를 직접 쓰고 거기로 섞는다.** 정면 평면성의 올바른 뜻은 "눌러서
얕게" 가 아니라 **"단면을 각지게"** — 초타원 지수를 올리면 두께는 유지한 채
중앙이 판판해지고 광대에서 꺾인다.

| | 중앙 | 광대 | 관자 |
|---|---|---|---|
| k=2.4 (두상) | 1.000 | 0.906 | 0.766 |
| **k=5.5 (앞면)** | 1.000 | **0.994** | 0.961 |

### 3.2 애니 얼굴에도 뼈가 있다

애니 두상은 뼈를 다 죽이지만 **0 으로 만들지는 않는다.** 코가 정확히 0 이면
옆에서 얼굴이 벽이 되고, 그게 '사람이 아니다' 로 읽히는 첫 신호다.

```
코        17.5mm   미간→코끝 능선, 폭 ±17mm    3/4 의 성패가 여기
눈두덩     4.2mm   전두골 미궁
안와      −3.2mm   눈알이 앉는 구멍
광대       3.8mm   얼굴에서 제일 넓은 지점
턱끝       6.0mm   하악 융기
하악각    k 2.4→2.9  둥근 타원은 턱이 없는 얼굴이다
```

### 3.3 로프트 윗면이 평평하면 어깨가 옷걸이다

사람 어깨는 목에서 팔로 **내려간다**(승모근→삼각근). `deform` 이 y 를 바꿀 수
있다는 점을 써서 바깥으로 갈수록 링을 내린다 — 목 둘레 ±32mm 는 안 내린다,
거기가 승모근이 솟은 자리다.

같은 부류: 목은 수직이 아니라 앞으로 10도(경추 전만) · 다리는 종아리 배가
있어야 죽마가 아니다 · 발은 앞으로 길고 뒤꿈치는 그대로.

### 3.4 머리카락은 두피를 **물어봐야** 한다

깊이를 사인 곡선으로 짐작했더니 앞머리 위쪽 절반이 두개골에 묻히고 끝만
삐죽 나왔다. `headFrontZ(y, x)` 가 답을 준다. 뒷머리도 같다 (`back: true`).

## 4. 그림과 셰이딩의 규칙

### 4.1 얼굴은 형태가 아니라 그림이다

머리는 단순하게 두고(정면을 각지게) **얼굴 한 장을 앞에서 투영**한다. 눈 하나가
열한 겹이다 — 눈구멍 · 홍채 그라디언트 · 방사 결 · 테두리 · 동공 · 하이라이트
둘 · 위 눈매 · 속눈썹 둘 · 쌍꺼풀 · 아래 눈매 · 애교살.

### 4.2 인상은 눈이 아니라 **눈썹**이 정한다

```
안쪽 +0.35h · 바깥 +0.10h   ← 안쪽이 더 낮다 = 찌푸린 눈썹
안쪽 +0.02h · 바깥 +0.34h   ← 바깥이 내려간다 = 순한 눈썹
```

눈을 한 픽셀도 안 건드리고 인상이 바뀐다. 같은 부류로 무섭게 만드는 것들 —
아래 눈꺼풀이 얕아 눈이 째짐 · 바깥 눈초리 치켜올림 · 순검정 눈매 ·
**작은 동공**(유형성숙: 작으면 노려보는 눈이다) · 넓은 흰자.

### 4.3 홍채는 눈꺼풀에 잘려야 한다

눈구멍 안에 쏙 들어가면 흰자가 넓어져 실사 눈이 되고, 그 순간 무섭다.

### 4.4 평행 투영은 z 를 안 본다

옆면과 뒤통수가 같은 u 를 받아 눈이 귀 뒤까지 늘어붙는다. 앞을 향한 면만
그림을 받고, 옆으로 돌아가는 면은 u 를 텍스처 가장자리(민 살색)로 민다.
실무 얼굴 언랩을 흉내내는 가장 싼 방법이다.

### 4.5 앞머리 그림자는 텍스처에 그린다

없으면 이마가 무한히 넓다. 지오메트리 그림자로는 이 모양이 안 나온다 —
가닥 하나하나가 그림자를 드리우면 지저분해진다.

### 4.6 선은 실루엣을 살리는 물건이지 모든 부품에 두르는 물건이 아니다

땋은 머리에 아웃라인을 씌웠더니 **은발이 흑발이 됐다.** 굵기가 아니라 형태
문제다 — 세 가닥이 서로 파고들어 홈이 깊은데, 뒷면만 그리는 껍질이 그 홈을
전부 메운다. 형태 자체가 굴곡으로 읽히는 것에는 선이 해가 된다.

### 4.7 림 라이트는 단계 램프 다음으로 크다

없으면 툰 셰이딩이 "색을 두 단계로 칠한 플라스틱" 이다. **얼굴에는 안 넣는다** —
가장자리가 밝아지면 그려 넣은 눈매 옆이 떠서 인상이 흐려진다.

### 4.8 파이프라인 주의

`MeshToonMaterial` 과 림 라이트는 **glTF 로 안 나간다** (표준 PBR 로 낮춰진다).
엔진 쪽에서 툰 셰이더를 다시 배정해야 한다. 반면 **아웃라인은 지오메트리라
그대로 나간다** — 그래서 셰이더가 아니라 역법선 껍질로 만들었다.

## 5. 결함 대장 — 반복된 종류

### 5.1 따라가야 하는 것이 안 따라간다 — **네 번**

| | 무엇이 | 무엇을 안 따라갔나 |
|---|---|---|
| 1 | 앞머리 | 두피 (사인 곡선으로 짐작) |
| 2 | 뒷머리 | 두개골 (좌표를 손으로 적음) |
| 3 | 스타킹 | 다리 (각자 자기 조종점 표) |
| 4 | 땋은 머리 고리 | 본 (정적 지오메트리) |

직접 조작에서는 일어날 수 없는 실수다 — 보면서 얹으니까. 코드에서는 관계를
하나하나 다시 유도해야 하고, 하나 빠뜨리면 **어떤 각도에서는 멀쩡해 보이는**
결함이 된다. 한 번 찾은 종류는 전수로 훑어야 하는데 그것도 어겼다.

### 5.2 정면에서 안 보이는 것은 정면만 봐서 못 잡는다

오목한 얼굴이 네 판을 버텼다. 3/4 로 돌려서야 드러났고, 사용자가 그려 준
그림 두 장이 렌더 열 장보다 정확했다.

### 5.3 굵기가 변하는 선은 **한 경로**여야 한다

되돌아오는 변이 `moveTo` 로 새 서브패스가 되어 눈매가 나비넥타이로 자기를
가로질렀다. 화면에서는 눈을 관통하는 가시로 보였다.

### 5.4 로프트 조종점은 y 오름차순

팔다리는 관절에서 아래로 적는 편이 자연스러워 내림차순으로 들어온다.
정렬 안 하면 마지막 구간으로 외삽해서 **팔이 2m 널빤지**가 됐다.

## 6. 하이브리드 — 검증된 배관

genex SKATE 를 열어 뭘 받아 가는지 읽었다. 매니페스트에 경로가 그대로 있다.

```
nano-banana-pro (컨셉) → meshy-6 (34만 면) → 1만 면 리메시(triangle)
  → meshy-biped 자동 리깅 → rigged-character.glb + core27 모캡
```

**사람은 코드가 아니다.** 전용 생성기 출력이고 코드는 그걸 움직인다.
그러면 코드 몫이 실제로 있는지가 문제고, 그걸 쟀다 (`__rig()`).

```
불러오기 5ms · 본 17 · 스킨드 6 · 클립 4 · 머리뼈 "Head" 발견
축척 1.104 자동 (상대 머리 높이에서 유도)
코드 생성물 20개 부착 · 삼각형 228 → 20,692
머리뼈 0.6rad 회전 시 머리카락 정점 이동 0.0771m   ← 따라온다
재출력 GLB: JOINTS_0/WEIGHTS_0 보존 · extensionsRequired 없음 · 블렌더 차단 없음
```

배관은 뚫려 있다. **빠진 조각은 베이스 메시 하나다.**

### 6.1 스프링 파라미터 — 쓸어서 찾았다

손으로 두 번 짐작해서 두 번 틀렸다 (중력이 이겨 몸을 뚫음 / 끝이 1.1m 튐).

| 강성 | 감쇠 | 정지 처짐 | 최대 이탈 | 최종 |
|---|---|---|---|---|
| 3 | 0.50 | 31mm | 506mm | 126mm |
| 3 | 0.85 | 31mm | **653mm** | 126mm |
| 6 | 0.70 | 16mm | 343mm | 118mm |
| **12** | **0.70** | **8mm** | **145mm** | 114mm |
| 24 | 0.70 | 4mm | 117mm | 113mm |

`최종 114mm` 가 강체였을 때의 이동량이다. 강성 12 에서 31mm 만 더 흘렀다가
돌아온다. 24 는 지연이 사라져 강체와 구분이 안 된다.

> **감쇠는 복원이 충분할 때만 도움이 된다.** 무른 사슬에서 감쇠를 올렸더니
> 돌아오는 속도까지 죽어 더 멀리 흘러갔다 (506 → 653mm). 직관과 반대라
> 쓸지 않았으면 못 찾았다. 필요한 강성도 첫 추정의 10배였다.

스키닝은 **UV 로 한다** — `sweep()` 의 v 가 이미 경로 위치(0 뿌리 ~ 1 끝)라
정점이 사슬 어디쯤인지가 적혀 있다. 좌표로 다시 찾으면 두 곳에서 계산하는 셈.

### 6.2 비용

`tools/meshy.mjs --plan` 이 계산한다.

```
--text   Meshy 키 1개 · 25 크레딧            ≈ $0.50   Pro 월 40회
--image  +Gemini 키  · $0.13 + 35 크레딧    ≈ $0.83   Pro 월 28회
```

`--text` 는 글에서 바로 만든다(프리뷰+리파인). 싸고 키가 하나면 되지만
생김새를 글로만 지시한다. **닮게 만들려면 `--image`** — 컨셉 이미지를 여러 장
뽑아 고른 뒤 한 장만 3D 로 올리므로 크레딧이 안 샌다.

> **API 는 유료 플랜 전용이다.** 무료 100 크레딧은 웹 UI 에서만 쓴다.
> 그래서 위 표의 "무료 월 n회" 는 성립하지 않는다 — 7장 참고.

크레딧 USD 단가는 **공개돼 있지 않다.** 위 환산은 Pro $20/1,000 에서 나눈
값이고, 실제 청구는 응답의 `consumed_credits` 로 확인한다.

### 마지막에 확인된 것 — Meshy API 는 유료 플랜 전용

무료 등급의 매달 100 크레딧은 **웹 UI 에서만** 쓸 수 있다. 설정 > API 탭이
통째로 잠겨 있고 "지금 업그레이드" 만 뜬다. `tools/meshy.mjs` 는 Pro($20/월)
이상에서만 돈다.

**다만 1단계는 돈 없이 된다.** 우리가 알고 싶은 건 "생성기 베이스 위에 우리
코드가 얹히나" 이고, 그건 GLB 파일 하나면 확인된다 — 웹 UI 로 무료로 만들어
내려받아 `web/export/` 에 두고 `__rig({ url })` 로 재면 뼈 이름·축척·두상이
그 자리에서 나온다. 스크립트는 그 뒤 자동화용이다.

### 다시 잡을 때 첫 한 수

1. Meshy 웹 UI 에서 무료로 하나 만든다 (Meshy-6 · 대칭 켬 · triangle 1만 면 · A-pose)
2. 자동 리깅 후 GLB 를 `web/export/` 에 둔다
3. `await __rig({ url: '/export/….glb' })`
4. 뼈 이름이 `findBone` 목록과 안 맞으면 `rigtest.js` 에 한 줄 더한다
