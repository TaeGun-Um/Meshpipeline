# 검증

> **갱신 (코드리뷰).** 검증 축이 넷이 됐다.
>
> | 축 | 무엇을 잡나 |
> |---|---|
> | `verify.mjs` 픽셀 회귀 | 결정성 파괴 · 재질 바인딩 · 지오메트리 누락 |
> | `__audit()` | 예산·규약·개수 하한·**비율** · NaN |
> | `__place()` | 관통 · 부유 · 도로 침범 |
> | **`district.byZone()`** | 구역별 표에 구역이 빠지면 **빌드가 터진다** |
> | **`tools/lumi.mjs`** | **밝기 위계** — 노면이 벽보다 밝으면 뒤집힌 것이다 |
>
> `lumi.mjs` 사용법:
> ```
> __shot({name:'_L_down',  pos:[-21,240,120], target:[-21,0,118]})   # 수평면
> __shot({name:'_L_wall',  pos:[-330,60,90],  target:[-190,55,60]})  # 수직면
> node tools/lumi.mjs web/shots/_L_down.png web/shots/_L_wall.png
> ```
> **수직면 평균 > 수평면 평균** 이어야 한다. 밤 도시에서 노면이 벽보다
> 밝을 이유가 없다 (레퍼런스의 노면은 젖은 아스팔트라 어둡다).
> 실측 기준선: 수평 11.1 · 수직 15.0
>
> byZone 이 새로 생긴 이유: 앞의 셋은 "값이 이상하다" 는 잡지만
> **"아무도 그 값을 정한 적이 없다" 는 못 잡는다.** 표에 구역이 빠지고
> `?? 0.2` 가 대신 정해도 개수·비율·픽셀이 전부 정상으로 보인다.
>
> **뷰 좌표는 도시 구조가 바뀌면 같이 썩는다.** 대지 병합 뒤 `corpo`·`deck`·
> `walk` 세 뷰가 건물 속으로 들어가 **검은 화면을 기준선으로 지키고 있었다.**
> 구조를 바꾼 뒤에는 `ls -l web/shots/nc_*.png` 로 유난히 작은 파일이 없는지
> 본다 — 검은 화면은 압축이 잘 되므로 크기로 걸린다.


무엇이 실제로 버그를 잡았고 무엇이 시간만 썼는지에 대한 기록. 새로운 점검을
만들 때는 아래 "실효 없었던 것" 을 먼저 읽는다 — 셋 다 그럴듯해 보였고 셋 다
틀렸다.

## 세 축

검증은 세 갈래이고 서로 보완재다.

| | 스크린샷 회귀 | 씬 감사 | 배치 검사 |
|---|---|---|---|
| 어디서 | `node tools/verify.mjs` | 콘솔 `__audit()` | 콘솔 `__place()` (감사에 포함) |
| 무엇을 | 화면이 달라졌는가 | 예산·규약을 어겼는가 | 물건이 서로 뚫거나 떠 있는가 |
| 강점 | 원인을 몰라도 변화를 잡는다 | 화면에 안 보이는 문제를 잡는다 | **어느 것이 어디서** 어긋났는지 |
| 약점 | **왜** 달라졌는지 모른다 | 아는 종류만 잡는다 | 보기 흉한 것은 못 잡는다 |

셋 다 필요하다. 파사드 시트를 1024에서 512로 내렸을 때, 감사는 텍스처가
350MB에서 189MB로 줄었다고 알려줬고 스크린샷 비교는 화면이 안 변했음을
증명했다. 한쪽만 있었으면 "줄이긴 했는데 뭐가 깨졌는지 모르는" 상태였다.

세 번째 축은 앞의 둘이 여덟 번 연속으로 놓친 종류를 위해 나중에 붙였다.
아래 참고.

## 스크린샷 회귀

```bash
node tools/verify.mjs              # 모든 씬
node tools/verify.mjs night-city   # 한 씬
```

브라우저에서 먼저 샷을 갱신한다.

```js
await __lock()          // 현재 상태를 shots/<이름>.png 로
await __lock('base')    // 기준을 새로 잡는다
```

### 기준선은 이미지가 아니라 (이미지 + 입력) 쌍이다

한동안 베이스라인 PNG 만 저장하고 카메라 좌표는 대화·콘솔에만 뒀다. 그 결과
기준선이 11장 있는데 **어떻게 찍었는지를 몰라 재현이 불가능**했고, 회귀 검증
도구가 통째로 무용지물이 됐다. 지금은 `web/shots/views.json` 이 유일한 출처다.

화면에 영향을 주는 상태는 **전부** 거기 적혀야 한다. 카메라만으로는 부족했다:
캐릭터가 있는 씬은 대기 동작 때문에 같은 씬을 두 번 찍어도 258픽셀이 달랐고,
`pose` 를 못박고 나서야 0이 됐다.

### 허용 오차는 0

같은 기기에서는 항상 정확히 0이 나온다. 0이 아니면 무언가 진짜로 바뀐 것이다.
이 엄격함 덕에 아래 버그들이 잡혔다.

- 리팩토링 후 난수 순서가 바뀌어 도시 전체가 달라짐 (26% 차이)
- `MeshBuilder` 의 그림자 기본값이 raw Mesh 와 반대라 차선 도색이 어두워짐
- `sphere()` 가 높이 분할을 폭에서 유도해 스카이라인 표시등이 달라짐
- `bindSet` 이 반복값 복제를 건너뛰어 텍스처에 옛 반복이 남음
- 텍스처 v축을 반대로 알아 점포 기단이 위로 감

### 뷰 고르기

서로 다른 거리대(눈높이·중경·항공)와 서로 다른 구역을 덮어야 한다. 한 각도만
보면 그 각도에서 안 보이는 회귀를 통째로 놓친다.

## 씬 감사

```js
__audit()
```

예산(삼각형·텍스처·드로우 그룹·프로그램·빌드 시간)과 파이프라인 규약을 점검하고,
텍스처 비용을 크기별로 분해해 보여준다. 규약 점검은 넷이다.

1. `emissiveIntensity !== 1` → `KHR_materials_emissive_strength`
2. `texture.repeat !== 1` → `KHR_texture_transform`
3. `color` 속성이 있는데 `vertexColors` 가 꺼짐 → 색이 무시됨
4. 빈 지오메트리 / 좌표에 NaN → 익스포터가 죽음

1과 2는 **브라우저에서는 완벽히 멀쩡해 보이는데** glTF 로 나가는 순간 비표준
확장이 붙는 문제다. 그 확장을 못 읽는 엔진에서는 조용히 무시되므로, 화면이
멀쩡하다는 이유로 넘어가면 안 된다 — 이 파이프라인의 1순위가 "브라우저와
엔진이 같아 보일 것" 이다.

### 발광 세기는 색에 곱해 넣는다

`emissiveIntensity` 는 **1이 아니기만 하면** 확장이 붙는다. 1보다 작아도 붙는다.
원래 규칙은 "1을 넘으면 예외" 였는데 전제가 틀렸고, `buildings.glb` 를 열어
`emissiveIntensity=0.22` 짜리 재질이 확장을 만드는 것을 확인하고 고쳤다.

three 의 셰이더에서 발광은 `emissive * emissiveIntensity` 이므로, 색에 미리
곱해 두고 세기를 1로 두면 화면은 완전히 동일하고 확장은 안 붙는다.
`core/material.js` 가 이제 이걸 강제한다.

## 개수 하한만으로는 절반이 죽은 것을 못 잡는다 — 비율

`__audit()` 은 예산(상한)과 개수(하한) 위에 **비(比)** 를 하나 더 본다.

```
길에 면한 면 0.52 · 건물당 간판 2.77 · 건물당 시설물 1.59 · 건물당 사람 13.2
```

### 왜 필요한가

간판이 1,602 -> 9 로 죽었을 때는 하한 200 이 잡아줬을 것이다. 그런데
1,602 -> 900 이면 하한을 한참 넘으므로 **아무 말도 안 한다.** 게다가 대지
병합처럼 건물 수 자체가 바뀌는 작업에서는 절대 개수로 "도시가 커졌다" 와
"결합이 깨졌다" 를 구분할 수 없다.

도시가 커지든 작아지든 **건물 한 채가 다는 간판 수는 크게 안 변해야 한다.**
변했다면 규모가 아니라 관계가 깨진 것이다.

### '길에 면한 면' 이 핵심이다

`towers.streetFaces` 가 인도 폭을 잘못 보는 순간 모든 건물이 "어느 면도 길에
안 면함" 이 되어 간판과 점포가 통째로 사라진다. 이 비율은 그 함수의
**직접 계측**이라 개수가 줄기 전에 먼저 떨어진다.

### 대역은 실측의 0.75~1.6배

좁게 박으면 변경마다 경고가 떠서 아무도 안 본다 (하한을 넉넉히 잡은 것과
같은 이유). 넣고 나서 **가짜 값을 넣어 실제로 발화하는지 확인했다.**

| 시나리오 | 결과 |
|---|---|
| 지금 그대로 | 통과 (거짓 경보 없음) |
| streetFaces 붕괴 (면한면 927→90) | **잡힘** |
| 간판 1,242→900 (28%) | **잡힘** |
| 간판 1,242→1,050 (15%) | 통과 — 의도한 조정 폭으로 본다 |
| 시설물 715→500 (30%) | **잡힘** |
| 사람 5,913→4,200 (29%) | **잡힘** |

즉 **25% 넘게 빠지면 잡힌다.** 그보다 작은 변화는 일부러 통과시킨다.

한계: 한 구역만 죽고 다른 구역이 메우면 전체 비율은 조금만 움직여서 못 잡는다.
구역별 비율이 다음 단계지만 아직 안 했다.

## 배치 검사

```js
__place()      // 관통·부유·차도 침범이 어디서 났는지
```

빌드마다 자동으로 돌고 `__audit()` 이 경고로 올린다. 손으로 부르는 검사는
안 부르게 되고, 안 부르는 검사는 없는 것과 같다.

### 왜 만들었나

같은 종류의 배치 오류를 여덟 번 냈는데 **앞의 두 축이 여덟 번 다 통과시켰다.**
"슬럼 골조가 옆 건물을 관통" 은 빌드 성공 · 감사 경고 0건 · 기준선 일치를
전부 통과했다. 개수도 안 줄고 삼각형도 안 늘었으니 당연하다.

### 세 번 틀리고 얻은 것

검사 자체를 세 번 틀렸다. 셋 다 다음에 또 저지를 만한 것이라 적어 둔다.

**1. 신고를 믿으면 같이 속는다.**
모듈이 "여기 이만한 것을 놓았다" 고 신고하게 만드는 쪽이 훨씬 쉽다. 그런데
슬럼 버그가 정확히 **회전 후 크기를 계산해 놓고 안 쓴** 것이었다 — 신고를
믿는 검사였으면 검사도 같이 통과시켰다. 그래서 `MeshBuilder.mark()` 로
구간을 열고 **그려진 지오메트리의 경계**를 읽는다. 인스턴스 메시는
행렬이 곧 배치이므로 행렬에서 읽는다. 어긋날 여지가 없다.

**2. 상수를 믿으면 상수가 틀렸을 때 같이 속는다.**
처음에는 차도를 `STREET_WIDTH/2` 로 정의했다. 당연해 보였다. 그런데 구간별
격자가 들어오면서 `BLOCK_SIZE + STREET_WIDTH` 가 피치와 안 맞게 돼 있었고,
검사가 그 상수를 믿는 바람에 **주차 1,137대가 인도에 서 있는 것을 통과시켰다.**
도로를 블록 판 사이의 빈 공간으로 다시 정의하고 나서야 잡혔다.

인수인계서에 "차량이 연석 안에 있나 — 손으로 해봤고 유효했다 (연석 11m,
최대 10.65m)" 라고 적혀 있었다. **그 손 검사도 11m 를 가정해서 통과한 것이다.**

**3. 상자 하나로는 "넓은 부분이 높이 있다" 를 표현 못 한다.**
디지털 수목의 우듬지가 차도 위로 뻗는 것을 "5m 침범" 으로 보고했다. 머리
위로 지나가는 가지는 결함이 아니다 — 실제 가로수도 차양도 그렇게 생겼다.
그래서 **4.5m 아래 조각만의 평면 범위**를 따로 잰다 (`placement.lowBox`).
데크 상판은 안 걸리고 그것을 받치는 기둥은 걸린다.

### 관측만 한다

도입 전후로 16뷰가 픽셀 단위로 동일했다. 지오메트리를 하나도 안 건드린다는
뜻이고, 그래서 작업 중인 씬에 넣어도 안전하다. 검사를 넣느라 대상이 바뀌면
그 검사 결과는 아무것도 증명하지 못한다.

## 실효 없었던 것 — 쓰지 말 것

### SHA256 파일 해시 비교

**거짓 실패**를 냈다. 디코드해 보니 RGB 와 알파가 바이트 단위로 완전히 같은데도
해시가 달랐다 — 스크린샷 파일이 다 쓰이기 전에 읽은 경합이었다.

거짓 실패는 거짓 통과만큼 나쁘다. 몇 번 반복되면 검증 결과 자체를 안 믿게 되고,
그때부터는 진짜 실패도 "또 그거겠지" 로 넘어간다. 이미지는 이미지로 비교한다
(`tools/compare-shots.mjs` — 의존성 없는 PNG 디코더 + 픽셀 비교).

### 존재 확인 없는 셸 비교

`certutil` 로 해시 둘을 비교하는 점검이 통과로 나왔는데, 실은 cwd 가 바뀌어
**두 개의 에러 문자열**을 비교하고 있었다. 둘 다 "파일을 찾을 수 없습니다" 라
같았던 것이다. 비교 전에 대상이 존재하는지를 먼저 단언한다 —
`tools/verify.mjs` 가 그렇게 한다.

### 추측으로 규약 정하기

두 번 시도했고 두 번 다 틀렸다.

- 텍스처 v축 방향 — `v=0` 이 아래라고 생각했는데 위였다. 빨강/파랑 시험용
  평면을 하나 띄워 재보고 알았다.
- `emissiveIntensity` 임계값 — "1 초과" 라고 생각했는데 "1이 아니면" 이었다.
  GLB 의 JSON 청크를 열어 `extensionsUsed` 를 보고 알았다.

규약은 재본다. 실측 비용이 몇 분이고, 틀리면 그 위에 쌓은 것이 전부 뒤집힌다.

## 규칙 대신 구조로

`texture.repeat` 문제는 "UV 를 지오메트리에 구울 것" 이라는 **규칙**으로 지키고
있었다. 도시 씬은 지켰고 공터 씬은 안 지켜서 22개 재질이
`KHR_texture_transform` 을 만들고 있었다 (8개 오브젝트 중 5개에서 실측 확인).

규칙은 사람이 기억해야 하고, 씬이 늘면 언젠가 또 안 지켜진다. 그래서
`Scene.build()` 마지막에 `meshkit.bakeTextureRepeat()` 을 공통 패스로 걸었다.
셰이더가 계산하는 `uv * repeat` 을 미리 UV 에 곱하고 repeat 을 1 로 되돌리므로
**결과가 완전히 동일**하다 — 두 씬 11개 뷰 모두 비트 단위로 같았고, 공터의
`KHR_texture_transform` 은 전부 사라졌다.

UV 하나로 표현할 수 없는 경우(offset·rotation·맵마다 다른 반복·공유 지오메트리의
배율 충돌)는 조용히 건너뛰지 않고 **예외를 던진다**. 조용히 넘어가면 "확장이
없어졌다" 고 믿는 채로 화면만 깨진다.

이게 이번 리뷰에서 가장 일반화할 만한 교훈이다. 검증으로 문제를 **발견**했으면,
같은 문제가 다시 생기지 못하게 **구조를 바꾸는** 데까지 가야 한다. 검증만
남기면 다음에도 똑같이 발견하고 똑같이 고치게 된다.

## 남은 것

`weeds.glb` 는 `EXT_mesh_gpu_instancing` 을 쓴다. 이건 의도한 것이고,
임포터가 못 읽으면 `__export('weeds', { bake: true })` 로 인스턴스를 실제
정점으로 구워 내보낼 수 있다.
