# 아키텍처

## 지배 원칙 세 가지

**1. 브라우저가 기준(reference truth)이다.**
"올바른 모습"의 정의는 브라우저 렌더다. 블렌더도 유니티도 그것을 재현해야 하는 쪽이고,
불일치가 나면 항상 브라우저가 아니라 하류를 고친다.

그래서 작업이 두 단계로 나뉜다. **설계 단계**에서는 브라우저에서만 반복하며 결과물을
다듬는다 — 이때 하류를 검증하는 건 기준이 아직 확정되지 않았으니 의미가 없다.
결과가 확정되면 **인계 단계**로 넘어가 파이프라인을 한 번 돌린다.

인계 이후에 하류를 고치는 동안에는 브라우저를 건드리지 않는다. 기준이 움직이면
비교 자체가 무의미해지기 때문이다.

**2. 규약은 한 곳에만 있고, 코드는 그것을 생성해서 쓴다.**
좌표계·스케일·정면 방향 같은 규약이 3개 언어 5개 파일에 흩어져 있었고, 그래서
한 곳을 고치면 다른 곳과 어긋났다. 지금은 `pipeline/contract.json` 하나가 출처이고,
C#·파이썬 상수는 거기서 **생성**된다. 코드에 숫자를 직접 적지 않는다.

**3. 검증은 눈이 아니라 숫자로 한다.**
"흔들리는 것 같다", "좀 어두운 것 같다"로는 회귀를 못 잡는다. 픽셀값·본 각도·삼각형 수를
재고 기준값과 비교한다. 모든 기준값은 실측으로 얻었고 근거가 규약에 주석으로 남아 있다.

## 브라우저 내부 — 세 계층

씬이 하나였을 때는 `core/`(엔진)와 정적 메시 모듈로 충분했다. 씬이 둘이 되면서
"공터 전용 재질 레시피 7종이 core 에 있다"는 문제가 드러났다. 판단 기준을 하나로 정했다:

> **둘 이상의 씬이 실제로 쓰는가.** 쓰기 시작할 때 올리고, 미리 올리지 않는다.

| 계층 | 무엇 | 예 |
|---|---|---|
| `core/` | **어떻게** 만드는가. 씬을 하나도 모른다 | 난수, 노이즈, 텍스처 굽기, 지오메트리 병합, 면 계산, 마스터 머티리얼, 메시 조립 부모 클래스, 씬 부모 클래스 |
| `shared/` | 둘 이상의 씬이 쓰는 **무엇** | 네온 팔레트, 도시 재질, 표의문자 간판, 빛 웅덩이, 항로 운동, 하늘돔 |
| `scenes/<씬>/` | 그 장소만의 배치·치수·고유 재질 | 도시 격자, 타워 구성, 고가도로 / 공터 지형, 한국식 주택 |

씬은 지우지 않고 쌓는다 (`scenes/index.js` 의 `SAVED`). 만들어 둔 씬을 그대로 다시 띄울
수 있어야 파이프라인 회귀를 재현할 수 있고, 리팩터링이 렌더를 바꾸지 않았는지 픽셀
단위로 검사할 수 있다.

## 부모 클래스 셋

세 곳에서 같은 코드가 반복되고 있었다. 반복을 없애는 것보다 **실수를 구조적으로
막는 것**이 목적이다.

**`core/material.js` — 마스터 머티리얼 (언리얼의 마스터/인스턴스와 같은 구조)**

```
마스터   셰이딩 모델과 파라미터 슬롯을 정의. 직접 쓰이지 않는다
파생     기본값 일부를 바꾼 새 마스터 = 상속
인스턴스 파라미터를 확정한 실제 머티리얼. 값이 같으면 같은 객체
```

```
TexturedSurface  SolidSurface  Glow ─┬─ NeonTube  SoftGlow  Beacon
                                Additive ─┬─ LightPool  Headlight
                                     Unlit
```

- **공유**: 값이 같은 요청은 같은 객체를 돌려준다. 나이트시티에서 발광 재질 요청
  956건이 머티리얼 6개로 접혔다.
- **오타 차단**: 슬롯에 없는 파라미터 이름은 즉시 던진다. three 의 머티리얼 생성자는
  모르는 키를 조용히 무시하므로, 예전에는 `roughness` 를 잘못 써도 아무 일이 없었다.
- **규약 강제**: `Glow.intensity > 1` 은 던진다 — glTF 로 나갈 때
  `KHR_materials_emissive_strength` 확장이 붙기 때문이다.

**`core/builder.js` — MeshBuilder**
`조각 수집 → 병합 → Mesh → 플래그 → Group → scene.add` 를 8개 모듈이 그대로
반복하고 있었다. 정점 속성 추가(빛 웅덩이의 색)도 여기서 처리한다.

**`core/scene.js` — Scene**
`meta` 기본값·검증, 환경맵 굽기, `build()` 오케스트레이션. 서브클래스는
`surfaceHeight()` 와 `createWorld()` 만 구현한다.

## 정적/동적 분리

메시 제작을 **정적**과 **동적**으로 나눈 것도 핵심 구조 결정이다. 둘의 요구가 다르다.

| | 정적 (`scenes/`) | 동적 (`dynamic/`) |
|---|---|---|
| 핵심 문제 | 텍스처, 인스턴싱, 배치 밀도 | 본 계층, 스킨 웨이트, 애니메이션 클립 |
| 최적화 | 병합 + `InstancedMesh` | 리지드 스키닝 (정점당 본 1개) |
| 익스포트 관심사 | 인스턴스 굽기, 정점 컬러 | 스킨·아마추어·액션 보존 |
| 엔진 소비 방식 | `MeshRenderer` + 콜라이더 | `SkinnedMeshRenderer` + `Animator` |

**공통은 `core/meshkit.js` 로 뽑았다.** 둘 다 "여러 조각을 하나의 `BufferGeometry`로
합친다"는 같은 문제를 푼다. 붙는 속성만 다르다:

- 인스턴싱: 인스턴스 행렬을 정점에 적용 + `instanceColor` → `COLOR_0`
- 스키닝: 본 rest 행렬을 정점에 적용 + `skinIndex` / `skinWeight`

의존 방향은 한 방향이다. `core` 는 `shared` 를 모르고, `shared` 는 `scenes` 를 모른다.

```
core/rng ─▶ core/noise ─▶ core/textures ─▶ shared/{urban, glyphs}
core/meshkit ─▶ core/boxfaces ─┐
core/material ─▶ shared/masters ┼─▶ scenes/<씬>/*
core/builder ──────────────────┘         ▲
core/scene ─────────────────────────────┘
core/meshkit ─▶ dynamic/*

## 동적 모듈의 설계 결정

**포즈 계산을 별도 모듈(`dynamic/pose.js`)로 뽑았다.**
실시간 재생과 클립 굽기가 **같은 함수**를 쓴다. 따로 구현하면 구운 클립이 브라우저에서
보던 동작과 어긋나는데, 그건 눈으로 확인이 안 된다. 같은 함수를 시간축으로 샘플링하므로
정의상 일치하고, 실제로 유니티에서 **0.23° 이내**로 재현됨을 측정했다.

**리지드 스키닝을 선택했다.**
부위가 전부 강체 박스이므로 정점마다 본 하나에 웨이트 1.0을 준다. 겉모습은 이전 강체
계층과 픽셀 단위로 같으면서 형식만 스킨드 메시가 된다. 관절 근처 웨이트를 섞으면
부드럽게 접히게 확장할 수 있고, 그때도 구조 변경은 필요 없다.

**본 이름을 유니티 휴머노이드 관례로 지었다.**
`Hips / Spine / Chest / Neck / Head / LeftUpperArm / ...` — 이 선택 하나로 블렌더 경유
FBX에서 유니티 아바타 매퍼가 자동 매핑되고, Mecanim 리타게팅을 쓸 수 있게 된다.

## 유니티 쪽 계층

```
Editor/ (에디터 전용, 배치모드 진입점)
  BuildScene              씬 조립 + Animator·콜라이더 배선
  AnimatorSetup           컨트롤러 생성 + 검증
  PipelineCheck           적합성 검사 49항목 (단일 진입점)
  ImportCheck             에셋별 상세 리포트
  TuneLighting            광원 격자 탐색
  CharacterModelPostprocessor  FBX 임포트 설정 강제
  PipelineContract.g.cs   생성된 규약 상수

Scripts/ (런타임)
  PlayerController        입력·물리·카메라·Animator 파라미터
  AcesTonemapper          ACES 톤매핑 (three.js와 동일 커브)
  WindTime                바람 셰이더 시간 공급

Shaders/
  VertexColorLit          정점 컬러 (잡석)
  VertexColorWind         정점 컬러 + 바람 (잡초)
  GradientSky             브라우저와 같은 5스톱 하늘
  AcesTonemap             three.js ACESFilmicToneMapping 포팅
```

**런타임 스크립트는 좌표계 규약을 직접 알지 않는다.**
`PlayerController.modelYaw` 는 씬 조립 시점에 `BuildScene` 이 규약에서 읽어 주입한다.
런타임 코드가 에디터 전용 클래스를 참조할 수 없기 때문이기도 하고, 규약이 코드에
박히는 것을 막기 위해서다.

## 왜 유니티 진입점을 하나로 묶었나

배치모드 1회당 고정 비용이 약 5.5초다 (라이선싱 1.6 + 도메인 리로드 2.4 +
스크립트 컴파일 0.5 + 에셋 리프레시 2.7). 실제 작업은 0.8초다.

즉 **작업을 나누는 것보다 프로세스를 나누는 것이 훨씬 비싸다.** 그래서
`BuildScene.All()` 이 컨트롤러 생성 → 씬 조립 → 렌더 → 애니메이터 검증을 한 번에 하고,
무거운 `ImportCheck` 는 `Full()` 로 분리했다. 개선 전 11.1초 → 개선 후 9.3초,
내 코드 구간은 2.18초 → 0.78초.

## 아키텍처가 막고 있는 실패

| 실패 유형 | 막는 장치 |
|---|---|
| 규약이 코드마다 달라짐 | 생성(`gen-contract.mjs`)이 파이프라인 단계 1 |
| 확정 전 결과물이 하류로 새어나감 | 설계/인계 단계 분리 — 설계 중엔 파이프라인을 돌리지 않는다 |
| 브라우저 수정 후 재익스포트 누락 | 단계 2 신선도 검사 (mtime 비교) |
| 메시 변경을 승인 없이 통과시킴 | `--accept` 가 내용 의존 값만 갱신, 불변식은 거부 |
| 애셋이 규약 위반 상태로 하류에 전달 | 단계 3 GLB 검사 (확장·루트·노말맵) |
| FBX 옵션 회귀 (`ARMATURE` 누락 등) | 단계 4가 아마추어·액션 수를 검사 |
| 좌표계·스케일·정면 회귀 | 단계 6이 키·발바닥·본 각도를 실측 비교 |
| 애니메이션 수식이 엔진에서 달라짐 | 단계 6이 손계산 포즈와 ±1.5° 비교 |
| 리팩터링이 렌더 결과를 조용히 바꿈 | 씬마다 기준 스크린샷 — `web/shots/baseline_*.png` 와 SHA256 비교 |
| 머티리얼 파라미터 이름 오타 | 마스터가 슬롯에 없는 이름을 던진다 |
| 같은 값 머티리얼이 중복 생성 | 마스터 인스턴스 캐시가 같은 객체를 돌려준다 |

## 삼각형 예산 — 측정하고 나서 깎는다

나이트시티가 130만 삼각형까지 불었을 때, 어디를 깎을지 **추측하지 않고 먼저 쟀다.**
그룹별로 세어 보니 `buildings` 가 73.8% 였고, 그 안에서 재질별로 다시 세니
`Duct` 45% · `Metal` 22% 였다. 둘 다 잔물건이었다.

측정이 세 가지 낭비를 짚어 줬다. **셋 다 화질 손실이 0 이다** — LOD 가 아니라
그냥 안 보이는 것을 안 만드는 것이다.

| 낭비 | 원인 | 처방 |
|---|---|---|
| 모따기 박스 9,900개 | 20cm 상품 상자에도 모따기(44 vs 12 삼각형) | `autoBox` — 최소 변이 0.55m 미만이면 그냥 박스 |
| 작은 구 80삼각형 | 10cm 전구를 8×5 분할로 | `sphere()` 가 반지름에 맞춰 분할 자동 선택 (5×3 = 20) |
| 안 보이는 면의 점포 | 블록 안쪽 필지의 면은 옆 건물과 1m 거리 | `streetFaces()` — 길에 면한 면에만 벽감·점포·간판 |
| 노면 페인트 박스 3,400개 | 윗면만 보이는데 박스(12 vs 2 삼각형) | 평면으로 |

결과: **1,298,950 → 720,382 (−44.5%)**. 건물만 958k → 478k.

원칙 두 가지가 남는다.

1. **깎기 전에 잰다.** 짐작으로 깎으면 눈에 보이는 것부터 깎게 된다.
2. **보이지 않는 것을 먼저 지운다.** 화질을 낮추는 LOD 는 그다음이다. 이 도시에서는
   화질을 하나도 안 낮추고 44% 를 줄였다.

빌드 시간(13.3초)은 지오메트리가 아니라 **텍스처 굽기**가 지배한다 (169장의 픽셀
루프). 삼각형을 더 깎아도 빌드는 빨라지지 않는다.

## 결정론 — 리팩터링을 검사할 수 있게 만드는 것

씬은 시드 하나로 완전히 결정된다. 그래서 스크린샷 SHA256 비교가 회귀 검사가 된다.
이 성질은 쉽게 깨지고, 깨져도 눈에 안 보인다. 실제로 깨진 방식 넷:

1. **난수 소비 순서** — 시드가 같아도 뽑는 순서가 다르면 다른 도시가 된다.
   특히 **객체 리터럴 안에서 난수를 뽑으면** 속성을 재배치하는 순간 순서가 바뀐다.
   그래서 난수는 반드시 지역 변수로 순서대로 뽑는다.
2. **런타임 상태** — 스크린샷 하네스가 바람 uniform·캐릭터 보행 위상·캐릭터 yaw·
   캐릭터 초기 위치를 전부 고정해야 두 번 찍은 결과가 같다.
3. **기본값 차이** — 맨 `new THREE.Mesh` 는 그림자 플래그가 꺼져 있고 `MeshBuilder` 는
   켜져 있다. 옮기는 순간 차선 페인트가 달 그림자를 받아 1/3 어두워졌다.

   길이에서 유도하면, 무관한 변경이 형상·텍스처를 바꾼다.
