# 개념 — 이 프로젝트가 하는 일

> 다른 문서보다 **먼저 읽는다.** 여기서는 "어떻게 짰나"가 아니라
> **"무엇을 하고 있는 것인가"** 를 다룬다. 코드를 처음 여는 사람도,
> 그래픽스를 해 본 사람도 여기서 좌표를 잡고 시작하면 된다.

---

## 1. 한 줄 요약

**외부 3D 애셋을 하나도 쓰지 않고, 코드가 계산한 숫자로 도시를 만든다.**
브라우저는 그 코드가 무엇을 만드는지 보는 창이고, 최종 산출물은 유니티에 들어가는
FBX 다.

저장소에 이미지 파일도 모델 파일도 없다. 화면에 보이는 건물 수백 채, 간판 천 장,
텍스처 백수십 장이 전부 **로드 시점에 함수가 만들어낸 것**이다.

---

## 2. 그래픽스를 배운 사람에게 — DX11 과 무엇이 같고 무엇이 다른가

DirectX 11 로 창을 띄우고, 삼각형을 그리고, FBX 와 텍스처를 불러와 화면에 올려 본
적이 있다면 이 절이 가장 빠른 입구다.

### 같은 것 — 파이프라인

밑바닥은 똑같다.

| DX11 에서 직접 한 것 | 여기서 대응되는 것 |
|---|---|
| `ID3D11Buffer` 정점/인덱스 버퍼 | `BufferGeometry` 의 position·index 어트리뷰트 |
| `ID3D11InputLayout` | 어트리뷰트 바인딩 |
| VS/PS 컴파일 | 머티리얼에서 GLSL 생성·컴파일 |
| `ID3D11ShaderResourceView` + 샘플러 | `THREE.Texture` |
| 상수 버퍼의 MVP 행렬 | uniform 으로 올라가는 같은 행렬 |
| `DrawIndexed()` | `drawElements()` |

Windows 크롬에서는 **그 아래가 실제로 D3D11 이다.** WebGL 호출이 ANGLE 이라는
번역 계층을 거쳐 D3D11 로 나간다. 개념이 비슷한 정도가 아니라 그 API 가 이 도시
밑에서 돌고 있다.

```
JS → three.js → WebGL2 → ANGLE → D3D11 → 드라이버 → GPU
                                   ↑ 그래픽스 과정에서 직접 짠 층
```

### 다른 것 — 숫자가 어디서 오는가

그래픽스 과정은 보통 두 단계를 밟는다.

1. **삼각형** — 정점 좌표를 코드에 직접 박아 넣는다
2. **FBX 로딩** — 정점 좌표를 파일에서 읽는다

이 프로젝트는 **1번을 극단까지 밀어붙인 것**이다. 화면의 `외부 애셋 0개` 가 그 뜻이다.

**GPU 입장에서는 둘이 구별되지 않는다.** 정점 버퍼에 float 이 들어가고 나면 그게
FBX 에서 왔는지 `Math.cos()` 에서 왔는지 알 방법이 없다. 차이는 렌더링이 아니라
**저작(authoring)** 에 있다.

텍스처도 같다. FBX 옆의 `.png` 대신 `bake()` 가 캔버스에 픽셀을 함수로 그려서
GPU 에 올린다 (`web/src/core/textures.js`).

### three.js 가 대신 해 주는 것

씬 그래프와 월드 행렬 누적, 머티리얼 파라미터에서 셰이더 코드 생성, 절두체 컬링,
리소스 수명 관리, 유니폼 갱신. 없어진 게 아니라 라이브러리 안으로 들어갔다.

## 3. 삼각형을 어떻게 찍는가 — "도형 단위"

정점 하나하나를 쓰지는 않는다. **도형 단위**로 찍는다.

보행로 가로등 하나가 이 한 줄이다.

```js
b.cylinder(0.16, 0.2, 4.6, [lx, Y + 2.3, lz], mats.metalMat, 8);
```

"윗지름 0.16, 아랫지름 0.2, 높이 4.6인 8각 기둥을 (lx, 2.3, lz)에 세워라."
이 한 줄이 정점 수십 개와 삼각형 30여 개를 만든다.

```
사람이 쓰는 것:   "여기에 이만한 상자"          ← 여기가 이 프로젝트의 내용
생성기가 하는 것: 정점 8개 + 인덱스 36개 생성   ← 정형화된 부분
GPU 가 받는 것:   삼각형 12개                   ← DX11 에서 본 그것
```

### 진짜 수학은 "어디에" 쪽에 있다

삼각형을 만드는 건 정형 작업이고, 이 프로젝트의 어려움은 **좌표를 정하는 쪽**에
전부 몰려 있다.

```
blockCenter(3) → -201          격자에서 블록 중심
  → P(a, sc * 9.5)             통로 축 기준 좌우 9.5m
    → lx                       가로등이 설 자리
```

**지금까지 낸 결함 중 삼각형이 잘못 만들어진 것은 한 건도 없다.** 전부 어디에
놓을지를 잘못 계산한 것이다 — 블록 사각형을 봐야 하는데 대지 사각형을 봤다든가,
회전한 상자의 축을 반대로 알았다든가. `docs/lessons.md` 2.1 결합 대장이 그 목록이다.

### 이어붙인다 — 문자 그대로

`b.add(...)` 는 그때그때 그리지 않고 **모아 둔다.** 다 모은 뒤 `b.build(scene)` 이
같은 재질끼리 정점 배열을 통째로 concat 해서 큰 버퍼 몇 개로 만든다.

```
삼각형 295만 개        ← 실제 삼각형 수
메시 56개              ← 그런데 드로우 대상은 이만큼뿐
재질 180개
```

건물이 283채고 간판이 1,762장인데 메시가 56개뿐인 이유다.
DX11 식으로 말하면 오브젝트마다 버퍼를 만드는 대신, 재질이 같은 것들의 정점을
하나의 거대한 버퍼에 이어 붙여 놓고 `DrawIndexed` 를 쉰여섯 번 부르는 것이다.

## 4. 브라우저에 보이는 것은 아직 파일이 아니다

자주 헷갈리는 지점이다.

| | |
|---|---|
| 지금 브라우저 | 편집기에서 코드가 **실행 중인 상태** |
| `.glb` | 그걸 **파일로 저장한 것** |

브라우저에 있는 건 JS 객체 그래프와 GPU 에 올라간 정점 버퍼다. `.glb` 는 그걸
직렬화한 결과물이고, 별도 단계(`web/src/export/gltf.js`)를 돌려야 생긴다.
안 돌리면 새로고침하는 순간 사라진다.

그래도 잃는 것은 없다. **코드가 결정론적**이라 같은 seed 로 돌리면 정점 하나까지
같은 것이 나온다. 픽셀 회귀 22장(도시 20 · 공터 2)이 매번 일치하는 것이 그 증거다.
**형태는 커밋되어 있고, 파일은 언제든 다시 뽑는다.**

## 5. 파이프라인 — glb 는 브라우저가 만든다

순서를 자주 거꾸로 안다. **블렌더가 glb 를 만드는 것이 아니라 받는다.**

```
브라우저(JS)            ← 도형 API 로 지오메트리 생성
   ↓  web/src/export/gltf.js
web/export/*.glb        ← glb 는 여기서 나온다
   ↓  tools/glb-to-fbx.py   (블렌더 --background, 파이썬)
unity/.../fbx_loose/*.fbx
   ↓
유니티 씬 조립 + 적합성 검사
```

MCP 같은 대화형 연동이 아니라 **헤드리스 배치 실행**이다.

```bash
blender --background --python tools/glb-to-fbx.py -- --mode loose --out ... a.glb b.glb
```

`node tools/pipeline.mjs` 한 줄이 6단계를 돈다. 자세한 내용은 `docs/pipeline.md`.

### 상시 도는 것이 아니다

| 단계 | 도구 | 파이프라인 |
|---|---|---|
| **설계** | 브라우저만 | 안 돎 |
| **인계** | 블렌더 → 유니티 | 한 번 돎 |

브라우저가 기준이므로 여기서 "올바른 모습"이 정해지고, 그 전에 하류를 검증하는 건
의미가 없다. 그래서 설계 중에는 파이프라인을 안 돌린다.

## 6. 무엇이 넘어가고 무엇이 안 넘어가는가

### 그대로 넘어가는 것

건물·도로·간판판·홀로그램 형상 — 전부 삼각형이라 잃을 게 없다. 텍스처도 구워 둔
캔버스를 PNG 로 박아 넣으면 된다.

### 손봐야 넘어가는 것 — `pipeline/contract.json` 에 규칙으로 있다

| 규칙 | 왜 |
|---|---|
| `bakeInstancedMeshes` | `InstancedMesh` 를 그대로 내보내면 `EXT_mesh_gpu_instancing` 이 **필수 확장**으로 붙고 개체별 색이 유실된다. 정점으로 구워 `COLOR_0` 으로 옮긴다 |
| `normalMapNotBumpMap` | **glTF 에 범프맵이 없다.** `bumpMap` 으로 내보내면 비표준 확장이 되어 블렌더·유니티가 통째로 버린다 |
| `rootTransformMustBeIdentity` | 런타임 좌표가 루트에 박히면 임포트 쪽에서 공중에 뜬다 (실측 y=1.1479) |
| `forbiddenExtensionsRequired` | `EXT_mesh_gpu_instancing` 금지 — 임포터 지원이 갈린다 |

### 안 넘어가는 것 — 유니티에서 다시 만들어야 한다

**가산합성(additive blending)이 glTF 에 없다.** 알파 모드는 `OPAQUE / MASK / BLEND`
셋뿐이다. 그런데 이 도시에서 가산합성으로 만든 것이 이만큼이다.

- 홀로그램 전부 (`holo()`, `holoSoft()`)
- **빛 웅덩이 전부** — 바닥·벽에 깔린 가산 지오메트리
- 간판 글로우 일부

형상은 넘어가지만 **겹칠수록 밝아지는 성질이 사라진다.** 유니티에서 Additive
셰이더를 붙여 되살려야 한다.

같은 성격으로 아예 지오메트리가 아닌 것들 — 안개, 환경맵(PMREM), 반구광·달빛,
하늘 그라디언트 돔. 이건 모델이 아니라 씬 설정이라 유니티에서 다시 세팅한다.

### 아직 안 정한 것

나이트시티는 **한 번도 내보낸 적이 없다.** `contract.json` 의 `exportedAssets`
목록은 전부 주택가 공터의 것이다. 인계 단계에 들어가기 전에 정해야 한다.

- 어떤 덩어리로 쪼갤 것인가 — 통짜 하나 / 구역별 / 건물 유형별 프리팹
- 브라우저에서는 드로우콜을 줄이려고 재질별로 합쳐 놨는데, 유니티에서 LOD·오클루전
  컬링을 걸 거면 **오히려 쪼개진 상태로 넘기는 편이 나을 수 있다**

## 7. 최적화는 여기서 하지 않는다

브라우저는 확인용이고 최종 산출물이 아니다. 삼각형 예산·드로우콜·프레임 타임을
**설계 결정의 근거로 쓰지 않는다.** 최적화는 유니티에서 한다.

다만 배치 검사(관통·부유·차도 침범)와 비율 지표는 성능이 아니라 **정확성**이므로
이 둘을 섞지 않는다. `docs/verification.md` 참고.

## 8. 도구와 버전

작업 시점의 실제 구성이다. 경로와 갱신 방법은 `docs/toolchain.md`.

| 도구 | 버전 | 역할 |
|---|---|---|
| Node.js | 24.15.0 | 오케스트레이터 · 개발 서버 · GLB 파서 · 검증 도구 |
| npm | 11.12.1 | |
| three.js | 0.185.0 | **유일한 런타임 의존성.** 빌드 도구 없이 importmap 으로 직접 로드 |
| Blender | 5.2.0 LTS (포터블) | 헤드리스 glb → FBX 변환 · 검증 |
| Unity Editor | 6000.3.11f1 (6.3 LTS) | 임포트 · 씬 조립 · 적합성 검사 |
| Unity glTFast | 6.19.0 | Unity 6.0 LTS 이상 요구 |
| Windows | 11 Pro 26200 | PowerShell 5.1 + Git Bash |

언어는 다섯이다.

| 언어 | 어디서 | 무엇을 |
|---|---|---|
| JavaScript (ESM) | `web/src/`, `tools/*.mjs` | 메시 생성 · 익스포트 · 오케스트레이션 |
| GLSL | `web/src/core/` 에서 주입 | 정점 셰이더 삽입 (바람 등) |
| Python 3 (bpy) | `tools/*.py` | 블렌더 헤드리스 변환 · 검증 |
| C# | `unity/Assets/` | 임포트 설정 · 씬 조립 · 적합성 검사 |
| HLSL / CG | `unity/Assets/Shaders/` | 톤매핑 · 하늘 · 정점 컬러 · 바람 |

빌드 도구(webpack·vite)를 쓰지 않는다. `web/index.html` 의 importmap 이
`node_modules` 를 직접 가리킨다.
